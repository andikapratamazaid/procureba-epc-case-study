# Data Model and Data Dictionary

**ProcureBA, EPC Procurement Digitalization Case Study**
ERD: `diagrams/erd.png`, generated by `diagrams/make_diagrams.py`.

## 1. Entity Overview

| Entity | Purpose | Key relationships |
|---|---|---|
| PURCHASE_REQUISITION | Header of a purchase request raised by a site requester | Has many PR_ITEM, APPROVAL, and PURCHASE_ORDER records |
| PR_ITEM | One requested line item on a PR | Belongs to one PURCHASE_REQUISITION and one ITEM_CATALOG entry |
| ITEM_CATALOG | Standard items with controlled specifications and reference prices | Referenced by many PR_ITEM records |
| APPROVAL | One approval step decision for a PR (supports multi-level chains and delegation) | Belongs to one PURCHASE_REQUISITION |
| VENDOR | Supplier master record including tier and bank data | Has many PURCHASE_ORDER records |
| PURCHASE_ORDER | Order issued to a vendor from an awarded quotation | Belongs to one PURCHASE_REQUISITION and one VENDOR; has many GOODS_RECEIPT records |
| GOODS_RECEIPT | One delivery receipt event against a PO (supports partial deliveries) | Belongs to one PURCHASE_ORDER |

## 2. Data Dictionary

### PURCHASE_REQUISITION

| Field | Type | Required | Description |
|---|---|---|---|
| pr_id | string (PK) | Yes | System-generated PR number, format PR-YYYY-##### |
| pr_date | date | Yes | Submission date and time |
| site | string | Yes | Project site raising the PR (5 sites in the case study) |
| requester_id | string (FK to user) | Yes | User who submitted the PR |
| category | string | Yes | Spend category, for example Mechanical Equipment |
| urgent_flag | boolean | Yes | True when submitted through the fast-track lane |
| status | string | Yes | Draft, Pending Approval, In Procurement, In RFQ, Quoted, PO Issued, Delivered, Closed, Rejected |

### PR_ITEM

| Field | Type | Required | Description |
|---|---|---|---|
| pr_item_id | string (PK) | Yes | Line identifier |
| pr_id | string (FK) | Yes | Parent PR |
| item_id | string (FK) | No | Catalog item; null for non-catalog requests with free-text specification |
| quantity | decimal | Yes | Requested quantity |
| unit | string | Yes | Unit of measure (pcs, set, m, kg, lot) |
| estimated_price | money (IDR) | Yes | Requester or catalog estimated unit price |
| line_total | money (IDR) | Yes | quantity x estimated_price, system calculated |

### ITEM_CATALOG

| Field | Type | Required | Description |
|---|---|---|---|
| item_id | string (PK) | Yes | Catalog identifier |
| item_code | string | Yes | Company item code, unique |
| item_name | string | Yes | Standard item name |
| category | string | Yes | Spend category |
| unit | string | Yes | Default unit of measure |
| standard_price | money (IDR) | No | Reference price, reviewed quarterly |

### APPROVAL

| Field | Type | Required | Description |
|---|---|---|---|
| approval_id | string (PK) | Yes | Approval step identifier |
| pr_id | string (FK) | Yes | PR being approved |
| approver_id | string (FK to user) | Yes | Approver (or delegate acting under the delegation rule) |
| approval_level | integer | Yes | Step order in the approval chain |
| decision | string | Yes | Approved, Rejected, Clarification Requested |
| decision_date | datetime | No | When the decision was recorded |
| remarks | string | No | Mandatory when the decision is Rejected |

### VENDOR

| Field | Type | Required | Description |
|---|---|---|---|
| vendor_id | string (PK) | Yes | Vendor identifier |
| vendor_name | string | Yes | Legal vendor name |
| tier | string | Yes | Performance tier A, B, or C, recalculated from the scorecard |
| contact_email | string | Yes | Address for RFQ and PO notifications |
| bank_account | string | Yes | Payment account; changes require second-person verification |
| status | string | Yes | Active, Suspended, Blacklisted |

### PURCHASE_ORDER

| Field | Type | Required | Description |
|---|---|---|---|
| po_id | string (PK) | Yes | System-generated PO number |
| pr_id | string (FK) | Yes | Originating PR |
| vendor_id | string (FK) | Yes | Awarded vendor |
| po_date | date | Yes | Issuance date |
| po_value | money (IDR) | Yes | Total PO value from the awarded quotation |
| promised_lead_time_days | integer | Yes | Lead time promised in the quotation |
| status | string | Yes | Issued, Acknowledged, Partially Delivered, Delivered, Closed, Cancelled |

### GOODS_RECEIPT

| Field | Type | Required | Description |
|---|---|---|---|
| gr_id | string (PK) | Yes | Receipt identifier |
| po_id | string (FK) | Yes | PO being received against |
| receipt_date | date | Yes | Date the goods were received at site or warehouse |
| received_by | string (FK to user) | Yes | Warehouse staff recording the receipt |
| qty_received | decimal | Yes | Quantity received in this delivery event |
| condition_ok | boolean | Yes | False flags a discrepancy workflow and blocks invoice matching for affected lines |

## 3. Data Notes

- The synthetic analysis dataset (`data/procurement_data.csv`) is a flattened extract of this model: one row per PR with stage dates, the awarded vendor, PO value, lead times, and delivery outcome. That is why the analysis can compute stage durations, scorecards, and maverick flags directly from it.
- Maverick purchases in the current (as-is) world exist outside this model entirely, which is precisely the control problem: in the to-be design, the fast-track lane keeps urgent purchases inside the same entities with `urgent_flag = true`, so they remain measurable.
- Vendor tier in the to-be design is a derived attribute, recalculated monthly from on-time rate and lead time (the scorecard method used in `analysis/kpi.py`: 60% on-time reliability, 40% lead time speed).
